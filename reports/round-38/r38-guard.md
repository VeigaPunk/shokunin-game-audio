## Fit record: setup versus numeric

The Round 38 scratch directory contains source-generated 2.0 s, 48 kHz mono PCM16 loop candidates. I used the project's own `measure_audio.py::measure()` implementation with the ambience spec `(2.0, 5, 200, True)` to measure fit candidates; I did not use source frequency/coefficient as a proxy for centroid. The base is the copied ambience canonical waveform (SHA `b18c81706fb03ecb51359bdf7045ef814dc28cbb51ce9b75fcda79a79fb5a198`, centroid `36.61640767851373 Hz`). Candidate `var_0.050.wav` measures centroid `41.247524622691245 Hz`, giving baseline-relative delta `0.126476550753913`; candidate `var_0.070.wav` measures `41.788029733727015 Hz`, delta `0.14123783252085534` (outside the preferred upper bound). The `.050` candidate's delta is strictly `>.10` and `<.13`. Its exact SHA-256 is `e6dbfa42c6d5dabebad65b2e2f3e13a87f0916d523775b6abc5b535439956fb4`; hashes differ from baseline. Both files measure 2.0 s, 48 kHz mono PCM16, and `measure()` reported empty ordinary/loop failures. Thus this is a successful local numeric fit, **not** proof that the opt-in runner path works or that the generic arm yields a recorded exit-0 receipt. The existing generic condition implies duration arm false and centroid arm true for this measured pair, but only integrated runner output can validate the intended control.

The inspected `alt/baseline.wav` + `alt/variant.wav` pair was also measured; its centroids are `91.03372963003302` and `81.6243985667145 Hz`, delta is below .10, so that candidate did not fit. No adjustment to `.020` or `.10` constants was made. A missing/invalid runner mode is an integration/setup gap, not a numeric fit failure. Candidate deltas outside the strict interval (including `.070`) are numeric fit misses, not setup failures.
