# Round 23 critic — challenge to the 13-file calibration table

## Finding

The 13-file table is viable only as a dated, fixture-local disclosure, not a replacement “calibrated threshold” claim. The round-22 normal receipt has 13 clean measurements and five distinctness records; its raw data support describing current gates. But a single 13-row summary can still mislead unless it separates per-file signal checks from subset-specific loop/section checks, names whether each comparator is inclusive, and distinguishes observed margin from demonstrated boundary behavior. Keep the old ten-file table as historical evidence; do not silently update its claims in place or suggest the old ten-file distributions include later fixtures.

## Falsification risks and required caveats

1. **Table scope and stale ten-file rows.** The existing `2026-10-12-threshold-calibration.md` explicitly anchors its distributions to the round-5 ten-file receipt and lists only four loop files / one section component. That evidence is not a present-day 13-file range. Add a separate dated/current section tied to before commit `64e6088794371769e31e0a6fc9ae0f2f2e0c91dd` and the round-22 normal receipt, with explicit eligible populations per rule. Current endpoint/slope checks apply to four loop WAVs; section component/contrast, internal joins and internal side slopes apply to different subsets. Do not apply one “13-file” denominator to every row. A threshold absent from a given file's measurement is not a zero observation.

2. **Controls do not uniformly isolate every row.** Round-22 evidence contains useful isolated probes: the normal 200 Hz join edge pass/fail pair straddles the `.03` comparator (`.029998779296875` passes, `.030029296875` fails); the side-slope edge pair similarly brackets `.001`: `.0009765625` passes and `.001007080078125` fails; both have contrast above 6 dB and internal adjacent jump `.000396728515625`. The slope positive/negative controls isolate that side-slope failure. The round-22 verifier documents flat30/flat120 contrast controls, reversed 180 Hz contrast, and 180/200 Hz join/slope probes, but most controls are far from the limit or also exercise other conditions. The damaged ambience fails both centroid and endpoint; it cannot validate either alone. Do not label a negative as isolating a gate unless the receipt's complete failure list shows that gate alone, and call edge pairs “tested points,” not validation of a continuous boundary or error rate. Rows without a named control should say “not exercised.”

3. **PCM width is not valid-bit precision.** Source `format_failures()` requires 48 kHz mono plus `codec_name == "pcm_s16le"` and `bits_per_sample == 16`. Round-22 `native16_probe` is the expected positive; matched `native24_probe` is the expected format failure. This supports a tested native PCM16/container-width policy, not inspection of the number of meaningful valid bits. The committed `r22-alt.md` reports an extensible 24-bit container with `wValidBitsPerSample=20` still appearing in the queried ffprobe fields as `pcm_s24le` / 24 bits. The current predicate rejects that encoding, but cannot tell 20 valid bits from 24. State explicitly that valid-bit handling is not measured and that `bits_per_sample` is not a valid-bits assertion. Do not claim broad WAV/container compatibility.

4. **JSON evidence is not a stable schema contract.** Round-22 normal measurements now include `codec_name` and `bits_per_sample`; invalid records add these fields selectively, and the invalid-mode root (`mode`, `invalid_probes`) differs from normal-mode root (`mode`, `thresholds`, `measurements`, `distinctness`, `sections`). Round 9 already deliberately renamed a section result key and removed a top-level frequency; its report notes unknown external consumers could break. No formal schema/version or external-consumer inventory is present. A table can disclose current receipt fields and historical mixed schemas, but cannot assert schema compatibility or promise an all-mode JSON contract. Mark compatibility as untested; preserve old receipts without rewriting them.

5. **LUFS remains descriptive only.** In the round-22 clean receipt, six short SFX readings are null; seven longer files have finite integrated LUFS (−15.8 to −32.7). The code maps missing/nonfinite/`<=−70` values to null. This is not a loudness acceptance window, not a measured −70 value, and not proof of silence or pass/fail loudness. A table should state “no LUFS gate / no acceptance window”; keep RMS dBFS as a separate linear-RMS-derived measure. Do not infer loudness calibration from the seven finite values.

6. **Margin arithmetic is not threshold justification.** For each bound, report clean range and nearest arithmetic margin only for the relevant subset, retain the actual code polarity, and state whether a control tests that same predicate in isolation. For example, duration fails only for `abs(error) > .001`; peak fails at `>= .95`; RMS fails at `< .001` (equality passes); centroid is inclusive; section contrast passes at `>= 6 dB`; component amplitude and section RMS floors are inclusive. The round-5 receipt key `rms_min_exclusive` is still legacy/misleading. The current table must follow source behavior, not its old JSON label. Also distinguish component-amplitude contrast (`20 log10(A2/A1)`) from integrated total section energy.

## Evidence examined

Read-only inspection of `measure_audio.py`, the round-22 LOG declaration, current round-5 knowledge table, committed round-22 verifier/adjudicator/alternate reports, and the committed round-22 raw normal, invalid, and edge receipts. Its section measurements include 30/120/180/200 Hz per-record component values; LUFS is null for six and finite for seven. The invalid receipt `.../20261013T010824568740Z-invalid/measurements.json` shows native16 expected pass and native24 expected format failure, alongside four prior invalid controls. Round-22 verifier records all 19 invocation outcomes and reports 13/13 canonical hashes plus five passing `_alt` checks. These are raw committed receipts and reports, not new playback or listening evidence.

## Verdict and limits

I do not find a reason the proposed table concept is impossible. I do find that it is falsified if “13-file table” is presented as a uniform population, threshold calibration, valid-bit guarantee, stable JSON contract, or LUFS target. Keep it as an appended, commit/receipt-anchored disclosure with per-row eligibility, source-exact polarity, observed margins, control isolation status, and explicit “not measured” entries. No threshold retuning or code change is supported by this review. No listening, engine/runtime, rights, export, or production claim is made.
